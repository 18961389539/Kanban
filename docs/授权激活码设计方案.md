# 看板系统 · 授权激活码设计方案（类 Windows 产品密钥）

> 范围：仅 MainAPP（WPF 桌面端，`net10.0-windows`）。Web 展示端（只读看板）不参与授权。
> 目标：用「机器绑定 + 离线激活码 + 30 天试用」替代当前硬编码的 `123456` 密码，做成一个可分发、难伪造、易管控的软件授权机制。
> 状态：本文件为设计文档，**不含实现代码**。

---

## 1. 总体架构

采用**离线机器绑定激活**（无需激活服务器），核心思路与 Windows 产品密钥一致：

```
用户机器                              厂商/管理员侧（持私钥，不发布）
──────────                            ──────────────────────────────
① 程序启动 → 计算本机机器码            ④ 管理员把机器码粘贴进「激活码生成器」
② 读 license.dat 判断是否已激活   ──→   生成器用 RSA 私钥对机器码签名
③ 未激活且试用已过期 → 弹激活窗口        输出 激活码 = Sign(机器码)
   显示机器码 + 激活码输入框         ←── ⑤ 用户把激活码填回程序
⑥ 程序用内置公钥验签 + 比对本机指纹        （试用期内无需此步，全功能可用）
⑦ 验签通过 → 写 license.dat → 已激活
```

不依赖任何后端服务；私钥只存在于管理员的「激活码生成器」小工具中，分发给客户的程序只内置**公钥**，无法自行伪造激活码。

---

## 2. 机器指纹（Machine Fingerprint）

用于把激活码绑定到具体一台机器，防止一个码在多台机器上复用。

- **采集来源**（取稳定、不易随系统重装变化的硬件标识，经 WMI / `System.Management` 读取）：
  - 主板序列号 `Win32_BaseBoard.SerialNumber`
  - BIOS 序列号 `Win32_BIOS.SerialNumber`
  - CPU 处理器 ID `Win32_Processor.ProcessorId`
  - 系统盘卷序列号（C: 的 `VolumeSerialNumber`）
- **计算**：将上述字段按固定顺序拼接 → `SHA-256` → 取前 8 字节 → 转 Base32 → 显示为 `XXXX-XXXX` 形式（即界面上展示给用户的「机器码」）。
- **容错设计**（建议，非必须）：硬件更换（如换主板）会导致机器码变化、原激活失效。可改为「N 个标识中 ≥2 个匹配即视为同一机器」，降低误锁。首版可先做单指纹（主板+BIOS），后续再上容错。
- **注意**：避免绑定 MAC 地址（USB 网卡/虚拟网卡易变），避免绑定用户名/计算机名（可改）。

## 3. 激活码格式与签名

- **激活码结构（明文载荷）**：
  `机器码 | 类型 | 过期时间 | 版本`
  - 类型：`PERMANENT`（永久）/ `TRIAL`（试用，可带过期时间，用于演示机）
  - 过期时间：Unix 时间戳；`PERMANENT` 填远未来日期（如 2099-12-31）
  - 版本：方案版本号，便于后续升级
- **签名**：用 **RSA（建议 2048 位，SHA-256）** 对明文载荷做签名；程序内置**公钥**验签，生成器持有**私钥**。
- **编码展示**：`载荷 + 签名` 整体做 Base32 → 按 `XXXX-XXXX-XXXX-XXXX`（4 组）格式展示，方便用户抄写。
- **为什么用 RSA 而非对称/HMAC**：程序只能验签、不能签名，私钥不落地到客户端，用户无法自行生成有效激活码（克服了当前 `123456` 明文密码谁都能用的致命弱点）。

## 4. 试用与锁定逻辑（未激活时）

你选择「限时试用 30 天」，因此有两道闸门：

1. **试用计时器**（无需激活码）：
   - 首次启动写入 `firstRunUtc`（UTC 时间）到 license.dat 的试用区。
   - 每次启动计算 `DaysLeft = 30 - (now - firstRunUtc)`。
   - `DaysLeft > 0`：全功能可用，主界面顶部显示「试用还剩 N 天」提示条。
2. **到期锁定**：
   - `DaysLeft <= 0` 且 `license.dat` 无有效激活 → 弹出激活窗口，**必须**输入有效激活码才能进入主程序（或仅保留「退出」按钮）。
3. **激活后**：写入永久激活记录，试用计时器失效，永久全功能。

> 反时钟回拨绕过试用：建议在 license.dat 记录 `lastSeenUtc`，若检测到系统时间倒退超过阈值，按已记录的最大日期计算剩余天数（增强项，Phase 4）。

## 5. license.dat 存储与防篡改

- **位置**：放入共享数据目录 `C:\ProgramData\Kanban\Config\license.dat`（即 `KANBAN_DATA_DIR` 指向的根，与现有 `devices.json`/三库同目录，便于统一备份迁移）。
- **内容**（推荐结构）：
  ```json
  {
    "machineCode": "K7F2-9XM4",
    "type": "PERMANENT",
    "issueUtc": 1788123456,
    "expireUtc": 4102444800,
    "firstRunUtc": 1788000000,
    "lastSeenUtc": 1788123456,
    "signature": "<RSA-SHA256 base64>"
  }
  ```
- **防篡改**：
  - 启动时先用内置公钥验 `signature`，且校验 `machineCode` 与当前本机一致；任一不符 → 视为无效（回到锁定/试用态）。
  - 文件整体用 **DPAPI**（`ProtectedData.Protect`，`CurrentUser` 或 `LocalMachine` 作用域）加密存储，避免明文被直接改。
  - 不做「永久有效」的明文兜底，杜绝改系统时间/改文件即可破解。

## 6. 与现有代码的集成点

- **启动闸门** `App.xaml.cs` 的 `OnStartup`：在创建 `MainWindow` 之前调用 `ILicenseService.GetState()`；
  - `Activated` → 正常启动；
  - `Trial` 且未过期 → 启动并在主窗口注入「试用还剩 N 天」横幅；
  - `Locked`/`TrialExpired` → 先 `ShowDialog` 弹出 `ActivationWindow`，确认激活成功后才建主窗口。
- **激活窗口** `ActivationWindow`（新建，风格复用现有 `PasswordInputDialog`：居中模态、`MainCard` 样式、`Enter` 快捷确认）：
  - 只读文本框显示**机器码** + 「复制」按钮；
  - 文本框输入**激活码**；
  - 「激活」按钮 → `ILicenseService.VerifyActivationCode(code)` → 成功写 `license.dat` 并关闭；失败给出红字提示。
- **激活码生成器**（独立的极小工具，持有 RSA 私钥，**不随产品发布**）：
  - 输入机器码 + 类型(+天数) → 输出激活码；
  - 可生成 `PERMANENT`（给付费客户）或带过期的 `TRIAL`（给演示机）。
- **既有 `123456` 密码的归宿**：当前「虚拟数据生成」的硬编码 `123456` 建议改为——仅当 `LicenseState == Activated` 才允许生成（或直接移除该密码，由授权状态接管）。这样授权与功能解耦，也更安全。

## 7. 防破解要点（ checklist）

- [ ] 程序只内置 **RSA 公钥**，私钥仅存于生成器（永不进客户端/仓库）。
- [ ] 激活码与**机器码绑定**，换机即失效。
- [ ] `license.dat` **签名 + 机器码 + 加密**三重保护，改文件/改时间均失效。
- [ ] 调试符号（`pdb`）发布时剥离；必要时加轻度混淆（如 Dotfuscator 社区版 / 重命名敏感方法）。
- [ ] 密钥与生成器放在独立私有仓库/受控环境，不进 `Kanban` 主仓库。
- [ ] 可选：启动后对关键授权判断加**周期性复检**（不只是启动时一次），防内存补丁。

## 8. 分期实施计划（仅步骤，不含代码）

- **Phase 1 — 核心服务**：实现 `ILicenseService` + `LicenseService`：机器码计算、RSA 公钥验签、license.dat 读写与 DPAPI 加密、状态判定（Activated/Trial/Locked）。
- **Phase 2 — 启动闸门与界面**：`App.xaml.cs` 启动校验；新建 `ActivationWindow`（复用 `PasswordInputDialog` 风格）；主窗口试用横幅。
- **Phase 3 — 激活码生成器**：独立小工具（持私钥），输入机器码+类型→输出激活码；内部留操作记录（谁、何时、给哪台机器发的码）。
- **Phase 4 — 加固**：反时钟回拨、周期复检、混淆/符号剥离、文档与交付（如何给客户发码的标准流程）。

## 9. 风险与注意

- **硬件更换导致误锁**：主板/BIOS 变更会让老激活码失效，需有「重新激活」流程（客户找管理员重发码）。容错指纹（第 2 节）可缓解。
- **私钥泄露**：一旦私钥外泄，任何人可自制激活码。生成器与私钥须严格受控；泄露后只能换密钥对并强制客户重新激活。
- **域环境可扩展**：若后续工厂是域环境，可进阶为「域账号/组 → 自动激活」，免机器码流程（作为后续可选演进，不在本期）。
