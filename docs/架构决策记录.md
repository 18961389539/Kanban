## ADR-1 每连接单长驻订阅（双/三连接设计）

**决策**：SignalR 每个 Hub 连接最多持有**一个长驻订阅流**（快照 / 报警+状态 / Meta），需要多流时用多个连接。

**理由**：SignalR 同连接内多个 `await foreach` 长驻读取是顺序执行的，多长驻会互相延迟（实测低频流被高频流拖慢约 13s）。单长驻 + 多连接是"按优先级隔离"的正确解：快照连接（500ms 高频）独立，事件连接（报警实时 + Meta 低频合并）独立。

**扩展模式**（新增数据流时先归类再落位）：
| 流类型 | 落位 | 例 |
|---|---|---|
| 高频全量（<1s） | 独占连接 | 快照流 |
| 事件边沿（实时性优先） | 事件连接 | 报警/状态事件流 |
| 低频元数据（>1s 可容忍） | 并入事件/Meta 连接 | Meta 流 |

**证据**：`KanbanDataClient`（Kanban.Client）、`RemoteRuntimeSink`/`DashboardState` 的双连接注释。

## ADR-7 同连接 Invoke 必须在长驻订阅之前完成

**决策**：任何 SignalR 连接上，**"客户端→服务端"的普通 Invoke（查询/拉取/写操作）必须在发起长驻订阅之前完成**；订阅占线后不得再同连接 Invoke。

**理由**：SignalR 服务端 `DefaultHubDispatcher` 对同一连接的 invocation **按接收顺序串行 dispatch**——第一个消息若是长驻订阅（Hub 方法不返回直到连接断开），后续所有 Invoke 会**无限排队**（既不返回也不报错，靠超时才能发现）。实测复现：主连接订阅快照后同连接调 `GetServerVersionAsync` 挂起 >3s（集成测试 `ConcurrentInvoke_WhileLongRunningSubscribePending_IsQueued` 锁定）；WASM 端曾因此"服务版本永远不显示、初始快照拉取永远挂起"（快照靠订阅推送补位而表面正常，隐蔽性强）。

**扩展模式**：
- 初始化顺序 = 先 Invoke（拉全量/版本等）→ 最后发起长驻订阅；
- 运行期需要查询时**不得复用长驻订阅连接**——开独立短连接（WASM `_metaClient` 只订阅；WPF `RemoteHistoryQueryService` 用独立 `_invokeClient` 即为此原因）。
- 服务端推送（OnSnapshot/OnMeta）不受此约束（无需客户端消息）。

**证据**：`Kanban.Web/DashboardState.SubscribeAndRefreshAsync` 的顺序注释；`KanbanDataClientIntegrationTests.ConcurrentInvoke_WhileLongRunningSubscribePending_IsQueued`。

## ADR-2 Collector 单写者（数据所有权）

**决策**：所有持久化写操作（devices.json / settings.json 采集子集 / work_orders.db / 4 个历史库）**只能由 Kanban.Collector 进程执行**；MainAPP 是管理入口（经 SignalR 转发），WASM 是纯展示（只读）。

**理由**：避免双进程写同一文件/库的冲突与丢失更新；历史库由持有采集管线的进程独占，崩溃恢复路径唯一。

**扩展模式**：新增任何"持久化配置/数据"时，写操作必须经 Hub 方法落到 Collector（如 `SaveDevicesAsync`/`UpsertWorkOrderAsync`/`SaveCollectorSettingsAsync`），MainAPP 侧只维护内存态。

**证据**：`DeviceRepository.RemotePersistenceHook`、`ConfigSyncHandler`、`ApplicationStartupCoordinator.StartRemoteDataLinkAsync`。

## ADR-3 单 Collector 部署边界（当前规模）

**决策**：当前部署形态为**单 Collector 进程**（采集全部设备 + 唯一 SQLite 写者 + WASM 静态托管），配 `sc failure` 自动重启 + 双端重连自愈。**不提前做多 Collector/高可用**。

**理由**：单点故障已有自愈兜底；多 Collector 引入数据源路由/聚合复杂度，对 <100 台规模是负收益。`/metrics` 的订阅者峰值、连接抖动、`PendingHistoryCount` 积压即扩容决策依据——触发条件（持续积压增长 / 单库 >2GB）出现前不改变此决策。

**扩展路径**（触发后再做）：按设备组分区部署多个 Collector，Hub 层加数据源路由；屏端按设备组连对应 Collector。

## ADR-8 数据采集容量基线与扩容触发条件

**决策**：数据源快照采用单 Collector 单写者、内存有界队列、JSONL 恢复文件和 SQLite WAL。容量判断以 `Append` 入队耗时、批量 Flush p95/p99、队列积压/溢出、恢复文件、WAL 和数据库文件大小为共同证据；在持续积压或存储阈值触发前不拆分 Collector。

**压测口径**：`DataSourceSnapshotCapacityBenchmark` 每台设备模拟 3 个数据源、每个数据源 4 个值项，每批记录数为 `DeviceCount * 3 * 4`。Release `ShortRun` 使用 3 次实际迭代、3 次预热，运行于 .NET 10.0.11 / Windows 11，使用与生产相同的 WAL 初始化。命令：

```powershell
dotnet run -c Release --project .\MainAPP.Benchmarks\MainAPP.Benchmarks.csproj --no-restore -- --filter "*DataSourceSnapshotCapacityBenchmark*" --job short --exporters json
```

**2026-08-20 观测基线**：

| 设备数 | 每批记录 | Append 入队均值 | Append+Flush 均值 | Append 分配量 | Append+Flush 分配量 | 末次主库 | 末次 WAL |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 20 | 240 | 37.53 us | 40.92 ms | 6.09 KB | 4,878.61 KB | 32 KB | 0.20 MB |
| 50 | 600 | 36.47 us | 53.15 ms | 20.95 KB | 12,040.35 KB | 32 KB | 0.43 MB |
| 100 | 1,200 | 87.57 us | 129.60 ms | 27.95 KB | 24,078.88 KB | 32 KB | 1.03 MB |
| 200 | 2,400 | 1.135 ms | 273.69 ms | 85.37 KB | 48,156.90 KB | 32 KB | 2.23 MB |

表中分配量是 BenchmarkDotNet 单次调用的托管分配，不等同于进程常驻内存。200 台 `Append` 的 3 次样本方差较大（标准差约 1.60 ms），因此这些数据是容量观测基线，不是固定 SLA。压测清理后各场景均为 `Pending=0`、`Overflow=0`、恢复文件 0 字节、Flush 失败 0 次，且 `TotalFlushedCount` 等于该批记录数；热身完成后的单批 Flush p95/p99 约为 16~34 ms，首次冷启动样本约为 184~194 ms。

**运行判据**：

| 指标 | 关注条件 | 处置 |
|---|---|---|
| 采集/Flush p95、p99 | Flush p99 连续 3 个诊断周期超过 500 ms，或采集 p99 接近/超过采集周期 | 先检查 SQLite/WAL、磁盘和 PLC 连接，再调整批量/周期 |
| 数据源队列 | `PendingCount` 持续达到 5,000（有界队列 10,000 的 50%） | 标记容量风险，观察是否持续增长 |
| 队列溢出 | `OverflowCount > 0` 或积压持续增长约 5 分钟 | 进入 Degraded，优先降低写入压力或扩容 |
| 恢复文件 | 超过 200 MB | readiness 返回 Degraded；保留 JSONL，禁止继续无限追加 |
| WAL | 定期 checkpoint 后仍连续两个周期超过 32 MB | 检查读事务、checkpoint 和磁盘 IO |
| 历史数据库 | 单库超过 2 GB，或队列/恢复文件同时持续增长 | 触发按设备组拆分 Collector 的设计评审 |

**证据**：`DataSourceSnapshotStore`、`HistoryStorageDiagnostics`、`DatabaseProvider.EnsureWalModeEnabled`、`CollectorMetrics`、`MainAPP.Benchmarks/DataSourceSnapshotCapacityBenchmark.cs`。

## ADR-9 数据源协议 reader 扩展边界

**决策**：数据源协议通过规范化的 `IDeviceAdapter.ProtocolKey` 选择唯一的 `IDataSourceReader`；连接配置中的 `PlcConfig.ProtocolKey` 持久化该选择，缺省值为 `plc`，旧配置继续兼容。reader 通过 descriptor 声明触发/值/回执能力及支持的值类型，并负责协议级地址校验和读写，`PlcScanPipeline` 只负责启用状态、触发语义、告警状态机和 cycle sample，`DataSourceSnapshotStore` 不感知协议。`DataSource.Type` 继续只表示业务展示类型，不作为协议键。

**连接档案边界**：`settings.json` schema 8 以 `ConnectionProfile.Id` 持久化命名连接档案，`Device.ConnectionProfileId` 只保存档案身份。schema 7 及更早版本的顶层 `PlcConfig` 迁移为 `default` 档案；顶层 `PlcConfig` 在过渡期保留为默认档案的兼容别名。`PlcRuntimeSessionManager` 以 profile ID 管理独立的 `PlcRuntimeProfileProvider`、driver router、driver 和 connection manager：default profile 复用既有 facade，其他 profile 按需创建并在配置刷新/移除时独立重配或释放。`DeviceAdapterResolver` 返回绑定到对应 session 的 adapter，DWord 批量缓存键包含 profile ID；采集读失败和扫描通信异常只标记受影响的 profile，避免一个 PLC 故障使其他 PLC 下线。旧构造器和 default facade 保留，兼容现有 WPF UI、Remote 模式和测试调用方。

**Profile 可观测性**：`PlcRuntimeSessionManager.GetDiagnosticsSnapshot()` 输出不含密码的连接与采集健康快照；采集循环按 profile 记录最近成功时间、最近失败时间、连续失败次数和累计失败次数。`CollectorDiagnosticsProvider` 将其同时投影到 Remote 诊断 DTO 与 `/metrics`，Prometheus 标签只使用有界的 `profile`、`protocol`、`brand`；`/health/ready` 只检查实际有可读地址设备引用的 profile，部分 profile 失败返回 `Degraded`，全部失败返回 `Unhealthy`，无 active profile 时保留空配置兼容语义。

reader 对外只返回协议无关的 `DataSourceReaderResult`（及泛型结果）和 `DataSourceReaderErrorKind`。PLC adapter 内部保留既有 `PlcOperationResult` 以维持低层驱动兼容性，由 reader 边界统一完成错误分类映射；调度层不再依赖 PLC 错误类型或原始运行结果。

**理由**：新增协议时，协议选择和地址规则不应扩散到调度循环；显式协议键也避免依赖 DI 注册顺序或 reader 优先级猜测。registry 在构造时拒绝同协议的重复注册，`Priority` 不参与隐式覆盖；运行诊断按协议暴露 resolve、校验、读写结果和耗时 histogram/p95/p99，便于区分协议故障与调度/存储瓶颈。

**扩展模式**：新增协议实现 `IDeviceAdapter` 与 `IDataSourceReader`，声明独立 `ProtocolKey`，通过共享 DI 注册；不修改 `PlcScanPipeline`、轮询调度或快照存储。第二个真实协议接入后，若协议依赖或发布节奏需要独立演进，再将实现迁入 `Kanban.Collector.Protocols.*` 项目；在此之前保持 Core 内单一 reader 边界，避免过早拆项目。

**证据**：`Kanban.Collector.Core/Models/PLCConfig.cs`、`Kanban.Collector.Core/Models/ConnectionProfile.cs`、`Kanban.Collector.Core/Models/Device.cs`、`Kanban.Collector.Core/Services/SettingsMigrationRunner.cs`、`Kanban.Contracts/Dtos/CollectorSettingsDto.cs`、`Kanban.Collector.Core/Mapping/CollectorSettingsMapper.cs`、`Kanban.Collector.Core/Services/PlcRuntimeSession.cs`、`Kanban.Collector.Core/Services/DataSourceReader.cs`、`DeviceAdapter.cs`、`PlcScanPipeline.cs`、`PlcDataAcquisitionService.cs`、`Kanban.Collector/Services/CollectorMetrics.cs`、`MainAPP.Tests/Unit/PlcRuntimeSessionTests.cs`、`MainAPP.Tests/Integration/PlcMultiProfileAcquisitionTests.cs`、`MainAPP.Tests/Unit/PlcBrandRegistryTests.cs`、`CollectorSettingsMapperTests.cs`、`DataSourceReaderRegistryTests.cs`、`DataSourceReaderContractTests.cs`、`CollectorMetricsTests.cs`、`ScanSourcesTests.cs`。

## ADR-4 单源计算约定（口径唯一）

**决策**：以下计算**全项目只实现一次**，禁止在两端/多处内联重复：
- OEE 四率：`OeeCalculator`（Kanban.Collector.Core）
- 快照展示换算（速度/不良率/时长占比/节拍/达成率）：`SnapshotMetrics`（Kanban.Contracts）
- 实体↔DTO 映射（Device/WorkOrder）：`Kanban.Core.Mapping.*Mapper`
- 采集设置/基线等配置：Collector 侧唯一落盘

**理由**：工厂数据口径（OEE 可用率是否含暂停等）跨端不一致是隐蔽线上事故；字段/口径变更只需改一处。

**证据**：`OeeCalculator`、`SnapshotMetrics`、`Mapping/` 的单源注释；WPF 与 WASM 共用。

## ADR-5 屏端零配置

**决策**：WASM 屏端启动不需要任何本地配置文件——设备列表/工单/班次/采集设置全部从 Collector 拉取或推送（`GetDevicesAsync` + Meta 流 + 快照流）。

**理由**：多屏部署时逐屏维护 devices.json 不可行；Collector 是配置唯一真源。

**证据**：`DashboardState`、`StartupCoordinator` 的"远程设备配置加载失败回退本地"逻辑。

## ADR-6 进程/项目边界

**决策**：
- `Kanban.Collector`：采集 + 历史存储 + SignalR 服务端 + WASM 静态托管（唯一写者进程）
- `Kanban.Collector.Core`：采集/存储/领域模型（MainAPP 与 Collector 共用，命名空间 `Kanban.Core.*`）
- `Kanban.Contracts`：DTO / Hub 契约（跨进程边界，**不得引用 Core/MainAPP**）
- `Kanban.Client`：SignalR 客户端库（WPF/WASM 共用，不依赖 UI）
- `MainAPP`：WPF 展示 + 管理（`MainAPP.Services` 仅 UI 服务；采集/领域一律用 Core）
- `Kanban.Web`：Blazor WASM 展示（只读）

**扩展模式**：新领域逻辑放 Core；新跨进程契约放 Contracts；新 UI 逻辑放 MainAPP/Web 各自侧。共享 DI 入口只有 `AddKanbanDataServices`。
